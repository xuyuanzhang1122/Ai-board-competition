## 本批结果

- `generateTextAsync` 原先在同一对象内调用 `@Async` 方法，绕过 Spring 代理，实际在提交线程生成。改为显式注入 `textTaskExecutor`；保存任务后只传任务及归属 ID，工作线程重新读取冻结快照并沿用条件抢占逻辑。
- 文本专用线程池核心线程 2、最大线程 4、等待队列 32。满载或关闭时拒绝，不能降级到 HTTP 线程执行。拒绝后条件更新 `PENDING` 任务为 `FAILED`，返回带任务 ID 的受理失败信息，不调用供应商或计费服务。
- 同步入口原先将任务创建、HTTP 和结果更新置于一个回滚事务内；失败记录可能整体消失，而且 `BusinessException` 分支直接重抛，不写失败状态。现在两个公开提交入口均使用 `NOT_SUPPORTED` 挂起调用方事务，任务创建与结果更新分别独立提交；业务异常先记录失败再抛出，调用方原事务随后恢复。
- HTTP 不占用该业务事务，供应商预算预留仍使用既有独立短事务。调用方回滚不再删除文本调用对应的任务快照、成功结果或失败信息。

当前工具箱和 `/api/generate/text` 实际仍使用同步 `generateText`。本批修复服务层异步入口，没有改变用户端协议或把工具箱切换为轮询。同步请求仍等待生成结束，不能将服务层异步测试描述为工具箱已实现异步交互。

## 验证证据

先运行新增回归，再实现修复：

1. 原异步提交在供应商受控阻塞时未能返回，线程池已满也未拒绝；修复后实际 Spring 注入的服务返回任务 ID，模型在工作线程执行，读取正确用户及快照；工作线程复用时没有遗留用户身份。
2. 原同步失败后数据库没有任务；只修事务后记录停留在 `RUNNING`，进一步定位到业务异常分支缺失状态更新。补齐后保留 `FAILED` 和原输入快照。
3. 使用真实 Spring 事务代理、MyBatis Plus 的生产 `JobMapper` 和隔离 H2 数据库，验证成功/失败记录在调用方回滚后仍存在，供应商调用时没有业务事务，异步任务在外层回滚后仍可读取并执行。
4. 实际生产线程池配置在满载及关闭后均拒绝任务，不在调用线程执行。
