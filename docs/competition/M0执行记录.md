## 环境隔离与启动前检查

| 项目 | 参赛环境约定 |
|---|---|
| Compose 项目名 | `ai-board-competition-dev` |
| MySQL | `127.0.0.1:13307`，数据库 `ai_board_competition`，用户 `competition` |
| Redis | 独立实例 `127.0.0.1:16379` |
| RabbitMQ | `127.0.0.1:15673`，管理台 `127.0.0.1:25673`，vhost `competition` |
| 后端/前端计划端口 | 后端 18080，用户端 13000，管理端 13001（尚未配置应用） |
| 文件存储 | 后续仅使用参赛专属目录或卷，禁止复用旧项目上传目录/COS 桶 |

原 `DotenvEnvironmentPostProcessor` 会将仓库 `.env`、`backend/.env` 加入高优先级属性源，此问题已修复。现在系统环境变量、Java 系统属性和命令行参数优先；未显式提供的值仍可从本机文件补充。正式启动后端前，仍须复核数据库、存储、队列、端口、JWT 和模型凭据的最终绑定，应用本身的配置文件也需检查。

隔离启动可选择以下一种模式：

- `APP_DOTENV_ENABLED=false`：不读取本机 `.env`；由独立启动环境提供全部必要配置。
- `APP_DOTENV_PATH=/绝对路径/competition.env`：只读取指定文件，不与仓库根目录或 `backend/.env` 合并。相对路径按进程工作目录解析；文件缺失或编码错误会拒绝启动，不回退读取旧文件。

未设置这两个选项时保留开发兼容行为：依次读取根目录和后端 `.env`，后端文件覆盖根目录文件；两者均不能覆盖系统环境变量或启动参数。此次修改只负责 `.env` 加载，并不等于已完成整个应用的运行隔离。

`spring.config.import`、激活 profile 等更早阶段选项仍应通过系统环境变量或启动参数提供，不依赖 dotenv。独立审查未发现阻塞问题；系统属性/包装器、相对路径成功和禁用优先的组合测试列为后续覆盖补充，当前未发现这些行为存在缺陷。

目前根目录 `docker-compose.yml` 仍为旧基线，不要用它启动参赛项目，也不要将新文件作为它的 override 合并。新文件不包含后端，因此不会触发 Flyway 或消费旧模型任务。

仅配置独立依赖时，可在填写独立密码后运行：

```bash
cp infra/competition/.env.example infra/competition/.env.local
# 编辑 .env.local，设置三项新密码；不要复用原环境凭据。
docker compose --env-file infra/competition/.env.local -f infra/competition/compose.yaml config --quiet
docker compose --env-file infra/competition/.env.local -f infra/competition/compose.yaml up -d
```

不要覆盖 Compose 项目名或选择原项目卷。端口被占用时先检查，不停止或修改原项目容器。
